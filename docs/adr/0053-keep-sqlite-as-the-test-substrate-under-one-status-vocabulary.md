# Keep SQLite as the test substrate under one status vocabulary

PostgreSQL is the pilot's database and the only runtime whose behaviour matters in production, which invites deleting SQLite so a single backend remains. That reading is wrong here: every `postgres_store.py` subclasses its `sqlite_store.py` sibling and swaps only the connection, so the SQLite stores hold the SQL PostgreSQL executes — deleting them would delete the PostgreSQL implementation and force roughly 2,100 lines of query logic to be rewritten with no test able to observe the result, since the suite runs on SQLite. SQLite therefore stays, positioned as the substrate the contract suite runs on and the offline development database, never as a second production store.

The problem worth solving is not two databases but two hand-maintained schema sources. SQLite creates tables with `CREATE TABLE IF NOT EXISTS` and has no migration runner, so an existing file keeps its old constraints and a status added to only one side stays invisible: a fresh test database accepts the write while the pilot rejects it. The contract suite consequently runs against PostgreSQL in CI as well, and a parity test compares the status vocabularies declared in the SQLite stores, the PostgreSQL migrations, the Voice Turn state machine and the kiosk event protocol, failing when any of them disagrees. A PostgreSQL-only backend remains reachable later by extracting the shared SQL into its own layer first, but only once the suite proves PostgreSQL behaviour, never as a deletion performed while SQLite is still the only thing under test.
