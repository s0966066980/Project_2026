# Run the Pilot on a read-only container contract

The Local Pilot ran on the development stack. `docker/compose.yaml` carries `APP_ENV: development`, `SECURITY_ENFORCED: "false"`, and a PostgreSQL URL with an inline password default, and the app and worker inherited it unchanged: non-root, which the Dockerfile had already settled, but with a writable root filesystem and the full default Linux capability set. The readiness record for that artifact said so in a note — a remaining hardening item, not a passed claim — which is the honest way to carry a gap and also the way a gap survives indefinitely. Two facts turned it from a note into a decision. The credential that the recorded Pilot evidence actually authenticated with was the compose default, not the value in the repository `.env`, because the stack had been started without it; and the profile the repository ships as the Pilot, `config/profiles/local-pilot.env.example`, names a `project_runtime` database role that nothing creates, so a Pilot started from it fails its first migration. A development stack cannot be made into a Pilot by intending it.

The Pilot is now its own overlay. `docker/compose.pilot.yaml` sets `read_only: true`, `cap_drop: [ALL]`, `no-new-privileges:true` and the numeric runtime principal on `migrate`, `app` and `worker`, and grants back exactly one writable path — `/tmp`, as `nosuid,nodev` tmpfs — because that is what the code needs and no more: runtime data already lives on the `app_data` volume, the model cache and media temp on the AI overlay's named volumes, and `docker diff` on an hour-old healthy app and worker container reports nothing written to the root filesystem at all. Configuration comes from three host-external files declared as `${VAR:?message}`, so an unconfigured Pilot fails at `docker compose config` rather than booting on development defaults and looking healthy. The database URLs from `compose.yaml` are cleared to empty so the `*_FILE` secrets are the only source, which the persistence profile already enforces by refusing a value and a file for the same name; it also refuses any secret file looser than 0600, so the host files must be owned by the runtime uid, and any other ownership fails closed rather than quietly falling back.

What this contract does not cover, it says out loud. `postgres`, `ollama` and `r1-omni` keep their upstream runtime contract: they are not our application code, they own their own data directories, and a read-only root filesystem imposed on them would be a claim no observed evidence here supports. The `project_runtime` role is provisioned and granted, but the application still connects as the owning role, so the least-privilege connection remains real convergence debt and belongs to the Operations & Configuration capability that owns database role and initialisation, not to this overlay.

The reason to put this in the runtime rather than in a checklist is the same reason [ADR-0021](0021-adopt-docker-first-immutable-pilot-delivery.md) pinned delivery to immutable images: a property that is only written down is a property that drifts. `UI_API/tests/test_pilot_container_security.py` reads the overlay as written, merge keys included, so a service that stops inheriting the hardening anchor, a capability added back without evidence, or a secret downgraded from a required host-external variable to a repository path fails a required check instead of surviving as a note in a readiness document.
