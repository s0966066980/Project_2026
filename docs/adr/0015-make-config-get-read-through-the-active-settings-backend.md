# Make config.get() read through the active settings backend

Status: accepted

`config.get()` — the dynamic-settings accessor used at over 200 call sites across the backend, including every Text Model Routing Policy and NIM Model Catalog lookup — now resolves through whichever settings backend is actually active. When `DATABASE_BACKEND=postgresql`, `config.load_settings()` reads through `commercial_settings_repository.get_settings()` (the same scoped, versioned store Admin writes to via `POST /api/settings`) instead of the local `settings.json` file; the JSON file remains authoritative only when Postgres is not in use. A 1-second TTL cache on the Postgres path matches the existing JSON mtime-check staleness bar, so this does not turn every `config.get()` call into a database round trip.

Before this, `config.get()` only ever read `settings.json`, regardless of backend. On a Postgres deployment — the project default — Admin's settings save went to `commercial_settings_versions` while every runtime reader kept reading the untouched JSON file. A saved change (starting with the NIM model, but in principle any setting read via `config.get()`) would appear to succeed in Admin and never reach the code that acts on it. `repositories/postgres_utils.py` already states the intended invariant — "never split authority by falling back to a different storage engine" — which this violated for the single largest settings consumer in the codebase.

We chose to fix `config.get()` itself rather than patch only the LLM routing keys. A narrow fix would have resolved the reported symptom while leaving the same class of bug live at every other one of the 200+ call sites, to resurface the next time an operator reports a setting that "doesn't seem to take effect." The broad fix costs more upfront risk — it changes the resolved value of every `config.get()` call under Postgres, not just the ones this task cared about — and needed a full pass to confirm no caller assumed JSON-only behavior. `repositories/commercial_settings_repository.get_settings_scoped()`'s no-row fallback also had to change, from returning `config.load_settings()` to returning `config.DEFAULT_SETTINGS` directly, to avoid a circular call back into the newly Postgres-aware `config.load_settings()`.
