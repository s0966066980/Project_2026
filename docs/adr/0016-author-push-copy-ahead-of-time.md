# Author push copy ahead of time instead of generating it per request

Status: accepted

AI Push Copy is now written in Admin and stored per menu item in `menu_item_push_copy`, and the Kiosk serves it with a plain lookup. `ai_push_service` no longer imports the LLM gateway at all; the only place a model touches push copy is the Admin authoring button. Each item carries two slots: a Base Push Copy that is always valid, and an optional Campaign Push Copy that names the offer it depends on and is served only while that offer is still in `rag_offer_service.load_active_offers()`. An item with neither falls back to the menu's own `description`. The same change applies to `/api/assist_recommend`, so both Kiosk surfaces show the same sentence for the same item.

Before this, every push generated a sentence through the LLM with the store's offers, RAG context and member preferences in the prompt, then ran `sanitize_unverified_promotion_claims` over the result to catch invented discounts. That put a model call on the customer's critical path for a sentence that is nearly always the same, and made three different failure modes (`fallback`, `guard_rewritten`, `client_error`) visible in telemetry for what the customer experiences as one push bar. Generation also cost a round trip per item on `assist_recommend`, which asks for three.

The trade-off we accepted is that copy no longer varies with the individual customer's cart or membership. That is a real loss and the reason this decision is worth recording: someone will eventually look at a static sentence and want to make it dynamic again. What we bought is that a push can no longer be slow, cannot fail, and — most importantly — cannot assert a promotion the store is not running. The Base Push Copy is refused at save time when it contains an unverified promotional term, rather than rewritten at serve time, because authored copy is shown to every customer until an operator edits it, whereas a generated sentence was only ever shown once.

Binding Campaign Push Copy to an offer id, rather than storing an expiry date next to the text, is what makes promotional wording safe to author at all. A campaign's lifecycle already lives in the campaign system; duplicating its end date into the copy record would create two sources of truth that drift the first time a campaign is paused or extended. Because the runtime check is "is this offer in the currently active set", an ended campaign silently stops showing its copy and the item reverts to its Base Push Copy with nobody having to remember. `load_active_offers()` is already called while building recommendation context, so this costs no additional query.

We considered keeping runtime generation and only using authored copy as the failure fallback. That would have preserved contextual copy, but it keeps every cost of the current design — the latency, the failure modes, the guard — while adding an authoring surface whose output customers would almost never see. Splitting the difference here would have been worse than either end of it.
