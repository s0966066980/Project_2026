# Publish store knowledge on save, and allow deleting it outright

Status: accepted

Saving a Knowledge Item now enqueues its publication immediately, and CSV import does the same for every row it creates. Operators no longer return to the list, tick checkboxes and press 「發布草稿」 — that step is gone from the interface. A new delete operation removes an item for real: it retires the item first so the retrieval index is cleaned, then purges the item and its versions, leaving only the audit trail behind. Retire is no longer offered on its own.

This supersedes the authoring half of ADR-0006. That decision gave each Knowledge Item a Draft lifecycle its author drives by hand, on the reasonable assumption that knowledge is written in one sitting and published in another. In practice a single store's knowledge base is a handful of short policy statements written by the person who already decided they should be live; the two-step flow asked them to confirm a decision they had just made, and the accumulating 「已退役」 rows made it progressively harder to see what still counted.

The publication module itself is unchanged, and Draft still exists inside it. This matters: indexing takes real time and can fail, so a save cannot synchronously become Published. What we removed is the operator's obligation to manage that intermediate state, not the state. The UI now reports 索引中 → 已上線 or the failure reason, and the only manual publication left is retrying an item whose index build failed — a recovery action, not a lifecycle step.

Deletion is a genuine reversal of ADR-0006's model, where withdrawal was terminal-but-retained. We accepted losing that history because the alternative — a list where every mistake stays visible forever — was actively making the surface harder to trust. Two things keep the loss bounded: the retirement path runs first so no orphaned content survives in the index (deleting the row alone would leave the chunks retrievable), and `knowledge_publication_audit` is deliberately exempt from the purge, so who deleted what and when is still answerable. Deleting an item that a Retrieval Test Case names as Expected Knowledge is allowed, but the interface lists the affected cases and requires confirmation first, because those cases fail silently otherwise.

CSV import publishing directly is the part most likely to be questioned later. ADR-0006's import was explicitly non-publishing so a bad batch could be reviewed before customers saw it. We accepted the change because the import already validates every row atomically and rejects the whole batch on any invalid row, so the content reaching customers has passed the same checks single-item authoring applies — and a reviewer who has to publish 40 rows by hand does not, in practice, read all 40.
