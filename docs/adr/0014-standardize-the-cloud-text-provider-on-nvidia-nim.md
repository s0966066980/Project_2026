# Standardize the cloud text provider on NVIDIA NIM

Status: accepted

The Cloud Text Provider is now fixed to NVIDIA NIM. Admin no longer offers a provider choice between Gemini and an OpenAI-compatible endpoint — the settings surface keeps the Text Model Routing Policy (local-first, cloud-first, local-only, cloud-only), and the cloud half of that policy always resolves to NVIDIA NIM. The Gemini adapter, its Vertex AI Express Mode / Developer API endpoint-selection logic, and the generic OpenAI-compatible adapter are removed from the gateway; NVIDIA NIM is reached through the same OpenAI-compatible chat-completions schema, since that is the protocol NIM speaks. Its credential (`NVIDIA_API_KEY`) and base URL (`NVIDIA_API_BASE_URL`) follow the existing rule that provider credentials live only in the environment, never in the versioned settings document.

Supporting two cloud providers cost more than it returned. The Gemini path alone carried Vertex AI Express Mode key detection, a cooldown and rate-limit state machine, and a JSON-mime toggle — code that existed only to compensate for that one provider's authentication and quota behavior. Every operational problem encountered with the cloud half of the chain in this project (401s from picking the wrong Google endpoint, 403s from disabled or unbilled Vertex projects) came from Gemini specifically. NVIDIA NIM was chosen over keeping the generic OpenAI-compatible adapter as the sole provider because the operator standardizing on it already holds NVIDIA infrastructure and credits, so this is not a speculative pick among interchangeable options — it is consolidating onto the vendor already in use elsewhere in the deployment.

We considered keeping the OpenAI-compatible adapter generic and simply defaulting its base URL to NVIDIA's endpoint, leaving the door open to point it at OpenAI or a self-hosted vLLM server later. That would have been a smaller diff, but it keeps a decision (which cloud service to use) alive in configuration that the operator has already made permanently; a stale "provider" field inviting a choice that no longer exists is exactly the kind of settings-surface confusion the routing-policy redesign in ADR 0013 was meant to remove. If a second cloud provider is needed later, it should be added back as a deliberate choice with its own adapter, not by generalizing this one further.
