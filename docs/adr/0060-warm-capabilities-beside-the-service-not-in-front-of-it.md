# Warm capabilities beside the service, not in front of it

The application lifespan awaited its warm-up before yielding, so uvicorn answered nothing until faster-whisper, the RAG embedding model and the voice model had loaded — while Docker had already published the port. A caller therefore got a connection that was accepted and then silent, which is the one failure a client cannot distinguish from a slow answer. `docker/compose.ai.yaml` had already recorded the price by overriding the app health check's `start_period` to ten minutes: on the documented GPU path, every restart could leave Admin and Kiosk device verification with nothing to react to for that long.

The blocking was deliberate and its reason was sound. [Voice Model Warm State](../../CONTEXT.md) puts model loading in service readiness rather than in the first customer's Voice Response Wait, and a comment in `bootstrap/startup.py` asked that neither port report startup complete before the shared warm-up finished. What made it wrong was scope, not intent. That comment protects the two-port host development servers in `bootstrap/server.py`, a path the Containerized Application Runtime no longer supports; applied to the whole HTTP service it let Optional capabilities hold Core ordering and the entire Admin surface down, which is exactly what Capability Criticality says must not happen.

Warm-up now runs beside the service. The lifespan starts it and yields immediately, and each capability carries its own state — pending, ready, failed or skipped — which `/ready` reports without counting: readiness stays the verdict of the required checks alone, so a model that is still loading is visible without being able to make the service look down. Voice keeps the gate the original decision was actually protecting: a Voice Turn is refused while its STT model is still loading rather than silently charging that load to the customer, which is the declared Voice Listening Unavailable state rather than an unexplained wait. A process that never started warm-up makes no readiness claim at all, so loading on first use remains the contract there and the gate stays out of the way.

This is [ADR-0059](0059-separate-emotion-configuration-from-runtime-readiness.md) generalised from emotion configuration to startup: what a capability is configured to do, and whether it can do it yet, are separate facts, and neither of them is the service's permission to answer.
