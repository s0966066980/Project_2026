總結一句：Roadmap 對「還沒做的事」誠實，對「已經有的事」樂觀。 它自評 Capability 0/10、Frontend 0/2，這個保守是準的； 但 §2.1「已具備」那一節的幾個詞——RBAC、module registry、typed client—— 讀起來像是機制已經接上，實際上機制存在、接線沒完成。 另外有兩件事任何文件都沒寫：一個閒置的第二資料庫正在跑，以及 ordering 的 SQL 由 SQLite 版本定義。

敘述容易高估的部分

以下四項的說法本身沒錯，機制確實存在。落差在於「存在」與「接上了」之間的距離， 文字沒有區分這兩者。

高估
RBAC：機制完整，但只掛在 6 個 operation 上
▶
文件認知
Roadmap §2.1「已具備」：「FastAPI 已有 route registry、typed /api/v1 envelope、 RBAC、commercial scope 與 OpenAPI。」
實際
RBAC 的資料層是真的：admin_roles、admin_role_permissions、 admin_user_role_assignments 三張表都有 DDL 與寫入路徑。 但在 139 個 HTTP operations 中，只有 6 處出現 require_permission。

如何解讀：Independence Gate 第 4 條要求「每個 operation 宣告 principal 與最小 permission」。 Roadmap 用 0/10 誠實反映了這條沒過，只是 §2.1 那句「已有 RBAC」單獨讀會讓人以為只剩收尾。

高估
9 張表有 schema、無寫入路徑、線上全空
▶
文件認知
Roadmap §4 把 fleet_* 列為 Identity & Device Access 的 data authority， recommendation_* 列為 Recommendation 能力的 data authority。 列在能力表上讀起來像是既有資產。
實際
這 9 張表有 migration DDL，但沒有任何程式寫入，線上 live rows 幾乎全為 0。 它們是預留的 schema，不是運作中的資料。
資料表寫入者線上列數
fleet_commands / fleet_config_versions / fleet_rollouts無0
recommendation_decisions / _governance_events / _strategies / _strategy_versions無0
promotion_rule_versions無0
rag_reset_receipts無1

如何解讀：Roadmap 已預告「Provisional data authority 必須在每個 slice 開始前校正」。 這 9 張正是需要校正的那一批——不是歸屬錯誤，是根本還沒有歸屬。

高估
ordering / checkout 的 SQL 由 SQLite 版本定義
▶
文件認知
README 與 Roadmap 通篇以 PostgreSQL 描述資料層。 ADR-0010 有提到 SQLite，定位是「Local Development/test adapter only」。
實際
PostgresCartStore 繼承 SQLiteCartStore， 沿用它的 SQL 字面，只替換連線與 ?→%s。 21 張表的 SQL 語句實際撰寫在 sqlite_store.py，執行在 PostgreSQL 上。
class PostgresCartStore(SQLiteCartStore): def _connect(self): return _Conn(postgres_utils.connect()) # q.replace("?", "%s")

如何解讀：這不算沒有文件——ADR-0010 承認 SQLite 存在。 但沒有任何文件說明生產路徑的 SQL 語意是由 SQLite 版本決定的。 Phase 5 要把 ordering 收斂成一個深模組時，這是必須先攤開的形狀。

高估
測試與 CI 的守備範圍比敘述窄
▶
文件認知
Roadmap §2.1：「Frontend 已有 Admin/Kiosk Vite entries、部分 typed client 與 少量 unit/E2E tests。」——「少量」只用來形容 frontend。
實際
Backend 同樣稀薄：8 個測試檔對 34,000 行程式碼。 CI 的 ruff 只 lint 一份白名單（main.py、app_factory.py、 api/、core/、models/ 與 2 個 repository 檔）， services/（16,676 行）與 modules/（7,768 行）不在其中。
層程式碼測試
Backend~34,000 行8 檔
Frontend~6,100 行3 unit + 1 e2e

如何解讀：Gate 第 6 條要求六類測試全通過才算一個能力完成。 以目前基數，第一個 slice 的測試工作量會遠大於搬移程式碼本身。

證據方法與界線

全部結論來自靜態掃描（SQL 字串常值、ast import 圖）、執行中容器的 OpenAPI 與 PostgreSQL 實測查詢， 以及 git 歷史比對。沒有做 runtime trace，所以「某段程式碼從未被執行」這類命題不在本報告的能力範圍內—— 報告中出現的「無寫入者」「不在 import 閉包內」都是靜態事實的陳述，不等於死程式碼的斷言。 兩處表名由變數組成、靜態無法解析（member_repository.py:427、 knowledge_publication/sqlite_store.py:1247），已排除在表歸屬統計之外。

可重跑的證據基礎：python3 tools/architecture_inventory.py 會重新產生 docs/architecture/inventory.json（表歸屬、引擎、process 歸屬的原始資料）。 本報告的判讀為人工撰寫，不隨腳本自動更新。
